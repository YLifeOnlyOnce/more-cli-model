# CLI 的构建原理与运行原理

这份文档专门讲底层原理，帮助你把“会用”升级成“知道为什么这样工作”。

## 一、构建的底层原理

这个项目的构建命令是：

```bash
npm run build
```

它实际执行的是：

```bash
tsc -p tsconfig.json
```

### 1. TypeScript 编译器做了什么

`tsc` 会读取 `tsconfig.json`，然后完成这些事情：

- 找到 `include` 中的源文件
- 按 `compilerOptions` 解析模块与语法
- 做类型检查
- 把 `.ts` 转成 `.js`
- 按 `outDir` 输出到 `dist/`
- 生成 sourcemap，方便调试

它不会替你“运行程序”，它只是把源码变成 Node 能执行的 JavaScript。

### 2. 为什么要有 `rootDir` 和 `outDir`

- `rootDir: src` 表示源码根目录
- `outDir: dist` 表示编译产物目录

这让源码和产物分离，便于发布和调试。CLI 运行时读的是 `dist/index.js`，而不是 `src/index.ts`。

### 3. `package.json` 的 `bin` 是怎么工作的

这里配置了：

```json
{
  "bin": {
    "learn-cli": "dist/index.js"
  }
}
```

这表示：当这个包被全局安装或通过 `npm link` 链接后，包管理器会为 `learn-cli` 创建一个可执行入口，它最终指向 `dist/index.js`。

在 Unix 环境里，通常会依赖 shebang 和软链接；在 Windows 环境里，npm 会生成对应的命令包装文件（如 `.cmd`）。

### 4. 构建阶段和运行阶段为什么要分开

因为 TypeScript 本身不是 Node 直接执行的标准格式。Node 默认执行的是 JavaScript，所以常见流程是：

1. 写 `src/**/*.ts`
2. 编译为 `dist/**/*.js`
3. 执行编译产物

某些工具如 `ts-node`、`tsx` 看起来像“直接运行 TS”，本质上也是在运行前帮你做了一层即时转换。

## 二、运行的底层原理

### 1. 操作系统如何启动一个 CLI

当你在终端输入：

```bash
node dist/index.js greet Alice --times 2
```

会发生这些事情：

1. Shell 解析这行命令
2. 启动一个 Node 进程
3. 把后续参数一并传给 Node
4. Node 加载 `dist/index.js`
5. 你的 JavaScript 代码开始执行

### 2. `process.argv` 是参数入口

Node 会把命令行参数放到 `process.argv` 中。

比如运行：

```bash
node dist/index.js greet Alice --times 2
```

那么大致会得到：

```js
[
  "node 的可执行路径",
  "dist/index.js",
  "greet",
  "Alice",
  "--times",
  "2"
]
```

所以 CLI 框架最核心的工作之一，就是把这一串字符串还原为结构化数据。

### 3. 参数解析器本质上在做什么

我们的解析器会把字符串数组拆成三类信息：

- 命令名：如 `greet`
- 位置参数：如 `Alice`
- 选项参数：如 `--times 2`、`--upper`

然后再根据命令定义做校验：

- 必填参数有没有提供
- 数量是否正确
- 选项是否需要值
- 用户是否传了未知参数

你可以把它理解成“把字符串协议翻译成程序对象”。

### 4. 命令执行本质上就是函数调用

当解析结果通过校验后，程序最终做的事其实很简单：

- 找到对应命令对象
- 把解析结果传给它的 `run` 函数
- 输出返回结果

也就是说，CLI 外表看起来是“敲命令”，底层其实是“命令字符串 -> 解析结果 -> 函数调用”。

### 5. 文件系统能力从哪里来

像 `json` 和 `note` 命令之所以能工作，是因为 Node 提供了标准库：

- `fs`：读写文件
- `path`：处理路径
- `os`：获取用户目录等系统信息

因此 CLI 可以轻松具备这些能力：

- 读取配置文件
- 生成代码模板
- 扫描目录
- 缓存数据
- 写日志

### 6. 错误处理为什么重要

CLI 不像 Web 页面那样可以靠界面兜底，它直接面对用户输入，所以要特别重视：

- 参数错误
- 文件不存在
- JSON 解析失败
- 权限不足
- 未知命令

好的 CLI 会给出清晰、可执行的错误提示，而不是只抛一个原始异常堆栈。

## 三、这个示例项目体现的设计思想

### 1. 分层

- `src/index.ts` 负责装配
- `src/core/` 负责通用解析
- `src/commands/` 负责具体业务
- `src/services/` 负责存储
- `src/utils/` 负责通用工具

这样做的好处是：以后命令越加越多时，不会全部塞在一个文件里。

### 2. 命令声明式定义

每个命令都通过一个对象描述：

- 名称是什么
- 参数是什么
- 选项是什么
- 帮助文案是什么
- 执行逻辑是什么

这让“命令定义”和“命令执行”分离，便于统一生成帮助信息。

### 3. 先设计数据结构，再写功能

CLI 很适合先设计类型：

- `CommandDefinition`
- `OptionDefinition`
- `ParsedCommand`

当类型清楚后，解析器和命令实现会更稳定。

## 四、从这个示例走向真实项目

真实 CLI 一般还会继续增加这些能力：

- 命令自动补全
- 彩色日志
- 交互提问
- 配置文件加载
- 网络请求
- 插件机制
- 单元测试
- 发布流程

但无论规模多大，底层主线都一样：

1. 接收输入
2. 解析输入
3. 调用逻辑
4. 输出结果
5. 处理异常

把这条主线真正理解，你就已经掌握了 CLI 工具开发最核心的部分。
